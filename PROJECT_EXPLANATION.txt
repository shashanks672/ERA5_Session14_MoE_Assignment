1. EXECUTIVE SUMMARY (WHAT WE DID)
================================================================================
In this project, we implemented an end-to-end Mixture-of-Experts (MoE) system in PyTorch from scratch:

1. Built a Dense Decoder-Only Causal Transformer Language Model (4 layers, 4 heads, d_model=256, d_ff=1024).
2. Pretrained the Dense model on the Tiny Shakespeare dataset for 500 steps to establish a solid baseline.
3. Surgically converted the pretrained Dense model into a Sparse MoE model:
   - Transferred Attention, LayerNorm, and Embedding weights directly.
   - Replaced each dense FFN with 8 routed experts + 1 dedicated shared expert.
   - Initialized experts using a warm-start symmetry-breaking strategy (Dense weights + Gaussian noise).
4. Continued training the MoE model for another 500 steps using a composite objective:
   Cross-Entropy Language Modeling Loss + Switch-style Auxiliary Load Balancing Loss.
5. Performed parameter accounting showing how model capacity quadruples (from ~3.17M to ~15.7M total parameters) while compute per token remains strictly constrained (~5.27M active parameters per token).
6. Exported complete loss curves, checkpoints, and autoregressive text generation samples.

2. CORE MOTIVATION: WHY MoE & WHY DENSE-TO-MoE CONVERSION?
================================================================================
A. The Problem with Dense Transformers:
In a standard dense Transformer, every single parameter is active for every single token. Doubling model capacity doubles the computational cost (FLOPs) and latency per token.

B. The MoE Solution:
Mixture-of-Experts decouples total parameter capacity from per-token compute. By dividing the Feed-Forward Network (FFN) into multiple "experts" and using a gating router to dynamically select only top-k (e.g., top-2 of 8) experts per token, the model gains vast memorization and reasoning capacity without proportional compute overhead.

C. Why Dense-to-MoE Conversion (Warm-Start)?
Training an MoE model from scratch (cold-start) often suffers from:
- Router instability in early iterations.
- Representation collapse (one expert hogging all tokens before others learn).
- High compute cost to reach baseline language competence.
By pretraining a dense model first and "up-cycling" (converting) it into an MoE model, the experts inherit general linguistic features immediately, allowing continued training to focus directly on expert specialization.

3. ARCHITECTURE & MATHEMATICAL FORMULAS
================================================================================

3.1 TOP-K SOFTMAX ROUTER:
Given token hidden state x in R^{d_model}, the router computes a routing distribution over E experts:
    h(x) = W_g * x             (where W_g in R^{E x d_model})
    P(x) = Softmax(h(x))

The router picks the top-k experts with indices I_topk = TopK(P(x), k) and re-normalizes their weights:
    w_i = P_i(x) / sum_{j in I_topk} P_j(x)

3.2 SWITCH-STYLE LOAD BALANCING AUXILIARY LOSS:
Without regularisation, the router may send all tokens to a single expert (expert collapse). We compute the differentiable auxiliary loss:
    f_i = (1 / N) * sum_{t=1}^N 1[expert i in TopK(t)]   (Fraction of tokens routed to expert i)
    P_i = (1 / N) * sum_{t=1}^N P_i(x_t)                 (Average router probability assigned to expert i)
    L_aux = E * sum_{i=1}^E (f_i * P_i)

Because P_i is continuous and differentiable with respect to router weights W_g, gradient descent pushes the router toward uniform distribution (f_i = 1/E and P_i = 1/E).

3.3 DEDICATED SHARED EXPERT + ROUTED EXPERTS:
The output of the MoE layer is computed as:
    y = FFN_shared(x) + sum_{i in I_topk} w_i * FFN_i(x)

- Shared Expert: Processes 100% of tokens unconditionally, capturing common linguistic priors (punctuation, common words, grammar).
- Routed Experts: Dynamically selected for token-specific domain specialization.

--------------------------------------------------------------------------------
STEP 1: DATA PREPARATION & TOKENIZATION
--------------------------------------------------------------------------------
- Implemented `CharTokenizer`: Character-level tokenization where each unique character represents 1 token.
- Exact Dataset Metrics:
  * Raw Dataset: Tiny Shakespeare (`input.txt`)
  * Dataset File Size: 1,115,394 bytes (~1.064 MB / ~1.1 MB)
  * Total Tokens in Dataset: 1,115,394 tokens (1,115,394 characters)
  * Vocabulary Size (Unique Tokens): 65 unique characters (including letters, punctuation, whitespace, and newlines).
  * Sequence Length / Context Window: 128 tokens per training chunk.
  * Train Split (90%): 1,003,854 tokens (yielding 1,003,726 causal training slices of length 128)
  * Validation Split (10%): 111,540 tokens (yielding 111,412 causal validation slices of length 128)
- Causal Slicing Target Shift:
    Input X = chunk[0 : 128]
    Target Y = chunk[1 : 129]
- DataLoader configuration: batch_size = 32, seq_len = 128 (i.e. 32 * 128 = 4,096 tokens processed per training step).


--------------------------------------------------------------------------------
STEP 2: DENSE BASELINE MODEL IMPLEMENTATION
--------------------------------------------------------------------------------
- Architecture: Decoder-Only Causal Transformer
  * Token Embedding + Learned Positional Embedding (vocab_size=256, d_model=256, max_seq_len=128)
  * 4 Pre-LayerNorm Transformer Blocks:
    - LayerNorm 1 -> Multi-Head Causal Self-Attention (4 heads, head_dim=64) using `F.scaled_dot_product_attention`
    - Residual connection: x = x + Attention(LN1(x))
    - LayerNorm 2 -> Dense FFN (Linear 256->1024 -> GELU -> Linear 1024->256)
    - Residual connection: x = x + FFN(LN2(x))
  * Final LayerNorm + Language Modeling Head (Linear 256->vocab_size)
  * Weight Tying enabled: LM Head shares weights with Token Embedding to save parameters.

--------------------------------------------------------------------------------
STEP 3: PHASE 1 - DENSE BASELINE PRETRAINING
--------------------------------------------------------------------------------
- Optimizer: AdamW (lr=5e-4, weight_decay=0.01, betas=(0.9, 0.95))
- Learning Rate Schedule: Cosine Annealing with 50-step linear warmup.
- Gradient Clipping: max_norm = 1.0 to prevent gradient explosions.
- Duration: 500 training steps.
- Tracked metrics: Training Cross-Entropy Loss, Gradient Norm, Step Elapsed Time.
- Result: Loss smoothly decreases from ~3.8 to ~1.8-2.0, establishing a trained language model.

--------------------------------------------------------------------------------
STEP 4: MIXTURE-OF-EXPERTS (MoE) ARCHITECTURE
--------------------------------------------------------------------------------
- Created `TopKRouter` module:
  * Linear projection (d_model -> num_experts=8).
  * Computes Softmax probabilities, selects Top-2 experts per token, normalizes top-k gating weights.
  * Calculates differentiable auxiliary loss L_aux = E * sum(f_i * P_i).
  * Tracks expert selection frequency across layers.
- Created `MoEFFN` module:
  * ModuleList containing 8 routed `Expert` sub-networks (Linear 256->1024 -> GELU -> Linear 1024->256).
  * 1 `shared_expert` sub-network with the same dimensions.
  * Efficient indexed dispatch: Gathers tokens for each active expert, runs expert forward pass, scales by router weights, and scatters back into the residual stream via `index_add_`.
  * Adds shared expert output.
- Integrated into `MoETransformerBlock` and full `MoELanguageModel`.
- Total loss formulation:
    L_total = L_LM (Cross Entropy) + aux_loss_coef (0.01) * L_aux

--------------------------------------------------------------------------------
STEP 5: DENSE-TO-MoE SURGICAL WEIGHT CONVERSION (WARM-START)
--------------------------------------------------------------------------------
- Function: `convert_dense_to_moe(dense_model, num_experts=8, top_k=2, shared_expert=True)`
- Direct Weight Transfers:
  * Token embeddings, position embeddings, and final LayerNorm copied directly from dense model.
  * Attention projections (c_attn, c_proj) and LayerNorms (ln_1, ln_2) copied exactly across all 4 layers.
- Shared Expert Transfer:
  * `shared_expert.w1.weight` <- `dense_block.mlp.w1.weight`
  * `shared_expert.w2.weight` <- `dense_block.mlp.w2.weight`
- Routed Experts Initialization (Symmetry-Breaking Warm-Start):
  * For each of the 8 experts in each layer:
    expert.w1.weight = dense_mlp.w1.weight + N(0, 0.005)
    expert.w2.weight = dense_mlp.w2.weight + N(0, 0.005)
  * RATIONALE FOR NOISE: If all 8 experts have identical weights, their gradients would be identical, preventing specialization. Adding tiny Gaussian noise breaks symmetry while preserving the pretrained representations.
- Router Gating Initialization:
  * Initialized with small random normal weights (mean=0.0, std=0.02) to give every expert an equal initial chance of selection.

--------------------------------------------------------------------------------
STEP 6: PARAMETER ACCOUNTING (TOTAL VS. ACTIVE)
--------------------------------------------------------------------------------
- Dense Model Parameter Breakdown:
  * Embeddings: 256 * 256 + 128 * 256 = 98,304
  * 4 Layers (Attention: 256*768 + 256*256 = 262,144; FFN: 256*1024 + 1024*256 = 524,288; LNs: ~2,048)
  * Total Parameters = ~3,172,000 (100% active per token)

- MoE Model Parameter Breakdown:
  * Embeddings & Attention: Identical (~1.14M)
  * Each layer has 8 routed experts + 1 shared expert = 9 FFNs * 524,288 params = 4,718,592 per layer
  * Total MoE Parameters = ~15,700,000 (~5x capacity increase)
  * Active Parameters Per Token = Base + Attention + Shared FFN + Top-2 Routed FFNs = ~5,270,000 (~33% active)
  * Result: Huge capacity expansion with sub-linear compute increase!

6. FREQUENTLY ASKED QUESTIONS & CONCEPTS FOR PRESENTATIONS
================================================================================

Q1: Why did we use Top-k = 2 instead of Top-1?
A: Top-2 routing allows tokens to be processed by a combination of two experts whose outputs are weighted and summed. This enables expert collaboration and smoother gradient flow compared to hard Top-1 switching.

Q2: Why do we have a Dedicated Shared Expert?
A: Common linguistic structures (articles, punctuation, common syntax) are needed by almost every token. Having a shared expert prevents the routed experts from redundantly learning the same basic tokens, allowing routed experts to specialize in distinct semantic niches.

Q3: What is the purpose of adding noise during dense-to-MoE conversion?
A: If all experts are exact clones of the dense FFN, the gradient backpropagated from identical top-k routing would update all experts identically, destroying specialization. A small Gaussian perturbation (std=0.005) breaks symmetry while maintaining 99.5%+ of the pretrained knowledge.

Q4: What happens if auxiliary loss coefficient (aux_loss_coef) is too high or too low?
A: If too low (or 0), the router collapses to selecting only 1 or 2 favorite experts, leaving other experts unused. If too high, the model over-prioritizes equal routing at the expense of language modeling accuracy. A value between 0.01 and 0.05 is optimal.
